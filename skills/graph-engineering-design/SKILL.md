# Graph Engineering 設計

対象リポジトリの実運用ワークフロー（複数の agent・loop・tool・人間判断の連なり）を、
「ノードが仕事をし、エッジが次を決める」明示的なグラフとして設計する。
出典は learn-harness-engineering lecture-14 / project-08 と、game-proposal-studio での
実設計（Experiment 1 → 全体レビュー → D決定 28 件）の試行錯誤。

**このスキルの成果物は設計書だけである。** グラフの実装（spec、runtime、ledger）や
既存 skill / rule / CLAUDE.md への適用は、人間が明示的に GO を出すまで一切行わない。

## 参照ファイル（必要時に読む）

| ファイル | 内容 | 読むタイミング |
|---|---|---|
| `references/patterns.md` | 構造設計パターン集（fan-out/fan-in、rollback 層、三グラフ分離、node contract、境界設計 等） | Phase 1 と Phase 3 |
| `references/process.md` | 試行錯誤から得たプロセス知見（暗黙エッジ狩り、レビューループ、決定台帳、禁止事項） | Phase 2 と Phase 4 |
| `references/templates.md` | graph.md / graph-design.md / 各台帳の骨格 | 初版執筆時 |

## 適用判定（着手前に必ず行う）

次の5基準のうち **3つ以上** を満たすか人間と確認する。満たさなければグラフは過剰であり、
直列の手順書（workflow script）を勧めて終了する。

1. タスクが独立・並列な作業単位に分解できる
2. 宣言する価値のある分岐・rollback 経路が存在する
3. 中間状態に checkpoint / resume の価値がある
4. 結果に機械検査可能な完了定義がある
5. 協調の利益が協調のコストを上回る

複雑さはグラフを要求しない。**分岐と rollback がグラフを要求する。**

## 成果物

| ファイル | 役割 | 契約 |
|---|---|---|
| `graph-design.md` | 設計根拠・検討過程・決定台帳・実装フェーズ台帳。歴史を保存する側 | 節単位で「凍結（実施時の写し）」と「現行」を区別。superseded は削除せず後続決定へのポインタを残す |
| `graph.md` | 現行設計の人間向け投影（Mermaid、ノード表、エッジ表、共有状態、ルーティング） | 常に最新の合意を反映。将来 spec（例: `graph.spec.yaml`）を正本化するなら「本書は生成物となる予定」と冒頭に明記 |

置き場所は対象リポジトリのルート（または人間が指定する場所）。

## 進め方

### Phase 0 — 対象の把握

1. 人間に質疑する: 何のワークフローをグラフ化するか、境界（どこからどこまでか、
   外部システム・別ハーネスとの接点）、実行主体の種類（human / agent / 決定論的コード）。
2. 既存のフロー記述を棚卸しする: CLAUDE.md、skills、rules、README、設計文書に
   **分散して書かれている制御フロー文**をすべて集める。グラフはこれらを1枚に落とす作業である。
3. maker（作る側）/ checker（検査する側）/ decider（決定者）の対応を表にする。
   決定者が人間なら「モデルが代理決定しない」ことをグラフの不変条件として最初に固定する。
4. 実行主体は**役割**として書く。モデル名は現在の割当の写しにすぎず、割当を変えても
   グラフ構造は変わらない旨を明記する。

### Phase 1 — 初版グラフ（6手順）

`references/templates.md` の骨格に沿って graph.md / graph-design.md の初版を書く。

1. **共有状態の定義** — ノード間で永続する状態（ファイル・フィールド）を列挙し、
   書く主体 / 読む主体 / 併合規則（append-only、上書き禁止、人間宣言後のみ等）を表にする。
2. **ノード列挙** — ID、責務、実行主体、主入力、主出力。ノードは決定論的コードでも
   完全な agent でもよい。agent ノードは自分の loop・private context・tool を内包する。
3. **エッジ列挙** — 分類を付ける: `seq` / `cond` / `loop` / `rollback` / `barrier` /
   `fan-out` / `forbidden` / `failure` / `boundary`。**矢印は作業順の推奨ではなく、
   実際に起こりうる遷移**である。禁止エッジ（存在しない遷移）も F 番号で明示する —
   文章規約はグラフ上「エッジの不在」として表現でき、違反検出が機械化できる。
4. **ルーティング規則** — ルーター（分岐点）ごとに if-then 形式で書き、**決定主体を併記**
   する（人間 / agent / 機械検査可）。どの条件にも該当しない応答のための catch-all
   （現ノードに留まり保留を記録、自動承認・自動却下しない）を全ルーター共通で置く。
5. **checkpoint と再開規則** — 何を実行位置の正とするか決め、再開規則 R0 を書く。
   並行分岐があるなら「現在位置」は単一ノードではなく active frontier の集合になる
   （`references/patterns.md` §正本の分離）。
6. **entry point とインスタンス単位** — 1インスタンス = 何か（1テーマ、1チケット、1 run）
   を定義し、thread ID に相当する識別子を決める。

### Phase 2 — 暗黙エッジ狩り

初版を描いた直後に必ず行う。`references/process.md` §暗黙エッジ狩り のチェックリストで、
**エージェントの推論内・その場の対話にしか存在しなかった判断経路**を探す。
発見は最低1件を目標にするが、チェックリストは全項目当てる。

発見は「指摘」で終わらせない。欠けているのがノードか、分岐の行き先か、エッジそのものかを
特定し、**対処後の設計としてグラフ本体へ反映してから** graph-design.md に発見の経緯を記録する。

### Phase 3 — 多重化・失敗・境界の設計

`references/patterns.md` のカタログを対象ワークフローに当て、該当するものだけ採用する。
最低限検討するのは:

- fan-out / fan-in（多重化はノードの複雑化ではなくグラフのインスタンス化で表現できないか）
- rollback の戻り先（欠陥の発生層へ戻す。最上位層の崩壊は同一 run の巻き戻しではなく
  successor run の新規起票にできないか)
- failure edge（agent 失敗、外部ツール unavailable、retry 枯渇を業務分岐と別 overlay で宣言）
- 別ハーネス・別リポとの境界（call-subgraph + typed boundary event。stale や状態を
  境界越しに自動伝播させない）
- 三グラフ分離（execution / artifact dependency / 組織学習を一枚に重ねない）

採用・不採用は候補ごとに人間へ諮り、graph-design.md の決定台帳（D番号）へ記録する。

### Phase 4 — レビューループ

`references/process.md` §レビューループ の手順で回す。要点:

- 人間がグラフ全体を読み、フィードバックを出す。弱点・論点は**提言台帳**（番号付き）に
  積み、採否はすべて人間が決めて**決定台帳（D番号）**へ記録する。
- 後続の決定が過去の決定を上書きしたら、旧決定を削除せず
  「superseded by D<n>」と追記して残す。設計の変遷自体が資産である。
- 「当面」「将来」等の**先送り表現を設計書に残さない**。条件付き確定・非目標化・
  機構化のいずれかに潰す。設計書に version 概念（v1 等）も持ち込まない。
- 人間が「設計完了」を明言するまで繰り返す。完了宣言もモデルは代理しない。

### Phase 5 — 完成と引き継ぎ

1. **GO 条件を文書完成にしない。** 実装 GO 後の完了条件を、実行・復旧・計測で定義して
   graph-design.md に書く（例: 全ノード直後の crash-resume、並行 frontier 復元、
   隔離の物理検証、failure fixture、最低2回の full pass と計測記録）。
2. **実装フェーズ台帳**を graph-design.md 末尾に置く。GO 後の適用順・依存・状態列を持ち、
   「次に何をすべきかはこの表を読んで判断する。会話の記憶を実行位置の正にしない」と明記する。
3. 人間に引き渡して終了する。**GO が出るまでハーネス実体に触れない。**

## 常時規律

- **決定はすべて人間。** 案の採否、設計完了、実装 GO をモデルが代理決定しない。
- **設計段階ではハーネス実体に触れない。** skill / rule / command / script / CLAUDE.md の
  変更は GO 後。設計中に「ついでに適用」すると差し戻しのコストが二重になる（実地の教訓）。
- **発見を指摘のまま放置しない。** 対処後の設計として本体へ反映し、経緯を根拠側に残す。
- **superseded を消さない。** ポインタ付きで保存する。
- **先送り表現・version 概念を書かない。**
- 結論先行。レビューで人間に渡すのは差分の要点とパスであり、全文の貼り直しではない。
