# プロセス知見 — 設計の試行錯誤から

game-proposal-studio で graph.md / graph-design.md を練り上げた過程（Experiment 1 →
暗黙エッジ発見 → 提言台帳 → 全体レビュー2巡 → D決定 28 件 → 実装 GO）から抽出した手順。
Phase 2（暗黙エッジ狩り）と Phase 4（レビューループ）で使う。

## 暗黙エッジ狩り

初版グラフを描いた直後に行う。狙いは「**文章規約としては存在する（または存在すべき）が、
遷移条件・記録義務・戻り先のいずれかが欠けているため、実行時はエージェントや対話の
暗黙判断で埋められていたエッジ**」。欠けているものは3種に分類でき、対処が異なる。

| 欠落の種類 | 症状 | 対処 |
|---|---|---|
| ノードの欠落 | 毎回行われている判定なのに、行う場所がグラフに無い | 判定ルーターを明示ノード化し、**判定結果の記録を義務化**する |
| 分岐の行き先の欠落 | 「検査する」とは書いてあるが、失敗したときどこへ行くか未定義 | そのノードの出口を全列挙して固定する |
| エッジそのものの欠落 | 起こりうる遷移（特に深い rollback）に対応する矢印が無い | エッジを新設し、既存の禁止規約と両立するか確認する |

### チェックリスト（初版の全ノードに当てる）

1. **checker 素通り検査**: checker を「呼ぶかどうか」を判定する分岐はどこで行われるか。
   その判定はノードとして存在するか。**「呼ばなかった」という判断は記録されるか。**
   軽微と誤判定すれば checker を素通りする経路になっていないか。分類基準は明文化されて
   いるか（「迷ったら重い側に倒す」— 自己分類バイアスは checker 素通りより安くつく）。
2. **全出口検査**: 検証・審査系の各ノードについて、通過 / 修正可能な失敗 / 致命的な失敗の
   3出口がすべて定義されているか。「致命的」の出口（kill・終端）を延命ループで代替して
   いないか。
3. **深い rollback 検査**: 下流の検証が上流の前提を崩したとき、その層まで戻るエッジは
   あるか。最上位層の崩壊時、禁止規約（再実行不可の工程）と衝突せずに戻れるか
   （→ successor run パターン、patterns.md）。
4. **並行時の合流検査**: fan-out がある場合、fan-in の招集条件・早期招集時の扱い・
   各入力の処遇記録は定義されているか。並行時に単独時の遷移（直行エッジ）が誤って
   使えてしまわないか。
5. **保留検査**: 人間の応答がどの条件にも該当しないとき（保留・追加情報待ち）の挙動は
   定義されているか（catch-all）。
6. **失敗検査**: agent 失敗・外部ツール unavailable・retry 枯渇の行き先はあるか。
   checker 不在時に「自動素通り」になっていないか。
7. **再開検査**: セッションが途切れた後、どの記録から現在位置を復元するか一意に決まるか。
   並行分岐があるとき「末尾の記録」で復元できるか（できない — frontier 集合が要る）。

発見ごとに graph-design.md へ「何が起きていたか / なぜ問題か / 対処後の設計」の3段で
記録し、**グラフ本体を先に直す**。発見リストだけ増やして本体を直さないのは失敗パターン。

## レビューループ

### 回し方

1. 人間にグラフ全体（graph.md）を読んでもらい、フィードバックを受ける。
2. フィードバック・自己発見の弱点を**提言台帳**（番号付き、対象・変更・状態の列）へ積む。
3. 論点になったものは**決定台帳（D番号）**へ切り出す: 問題、検討した代替案（表で比較）、
   決定、理由、反映先。**採否を決めるのは常に人間。**
4. 承認された設計をグラフ本体へ反映し、台帳の状態列を更新する。
5. 数巡ごとに「全体レビュー」を行う: 個別修正の積み重ねで生じた不整合（用語、正本の重複、
   一枚に重なった別グラフ）を洗い、必要なら設計を再編する。
6. 人間が完成を明言するまで繰り返す。

### 台帳運用の規律

- **決定は D 番号で通し、採否記入欄（論点 / 採否 / 日付 / 理由）を一表で持つ。**
  後から「なぜこうなっているのか」を辿る唯一の入口になる。
- **supersede の扱い**: 後続決定が過去の決定を上書きしたら、旧決定の本文に
  「後続決定による更新: D<n> により superseded」と追記して残す。削除しない。
  提言台帳側も同様（状態列に superseded by D<n>）。
- **凍結と現行の区別**: 初版実施時の記録（Experiment の写し）は凍結節として保存し、
  冒頭に「§X〜Y は実施時の写しとして凍結。現行設計は §Z」と書く。比較記録として
  暗黙エッジ発見の再現性を保つため。
- **推奨と決定を混ぜない**: モデルの推奨案が人間に却下されたら、却下の経緯ごと台帳へ
  残す（「当初推奨は X だったが人間が却下、Y を採用」）。後で推奨が再浮上するのを防ぐ。

### 表現の規律

- **先送り表現の全廃**: 「当面」「将来〜した時に」を残さない。全箇所を洗い出し、
  (a) 観測可能なトリガー付きの条件付き確定、(b) 非目標化（再検討には新しい人間決定を
  要すると明記）、(c) 機構化、のいずれかへ潰す。
- **version 概念を持ち込まない**: 設計書に v1 / v1.1 等を書かない。歴史は git と台帳が持つ。
- **名前の衝突検査**: 同じ語が別の成果物を指していないか（例: 消費側に見える名前と
  内部構造の名前の上下逆転、既存成果物との kind 衝突）。改名は実装が無いうちに行えば
  コストゼロ — 逆に言えば、実装前が名前を直す唯一の安い時期。

## 実装との分離（最重要の教訓）

**設計段階ではハーネス実体（skill / rule / command / script / 最上位規約）に触れない。**

実地で一度、設計中に実体へ適用して差し戻された。以後「提言はすべて承認済みでも、
適用は人間の GO 後」を固定した。理由:

- 設計はレビューループで書き換わる。実体を先に変えると、設計変更のたびに実体も
  巻き戻す二重コストが発生する。
- 関連する契約（skill と rule の対）は一括適用しないと食い違う。適用順は依存関係を持つ
  ため、設計完了後に台帳で順序立てて行う方が安全。

### 実装フェーズ台帳

設計完了時、graph-design.md 末尾に GO 後の適用順を表で置く:
フェーズ / 内容 / 対象（提言・D番号） / 依存 / 状態（未着手・進行中・完了・差戻し） /
成果物パス。冒頭に次を明記する:

> 次に何をすべきかは、この表を読んで判断する。会話の記憶や外部メモリを実行位置の
> 正にしない。フェーズ着手時・完了時は必ずこの表の状態列を更新すること。

これは設計対象のグラフに適用する「machine ledger が実行位置の正」という原則を、
実装作業自体へ自己適用したもの。

### GO 条件は実行・復旧・計測で書く

「文書が完成した」を GO 条件・完了条件にしない。例:

- 全ノード直後の crash から重複 write なしで resume できる
- 並行 fan-out の active frontier を復元できる
- ブラインド / auditor ノードが禁止ファイルを物理的に読み書きできない
- timeout・retry 枯渇・partial failure・human overdue の fixture が通る
- stale input が下流を block し、repair 後に元 branch へ戻る
- spec から生成した文書と runtime router の edge 集合が一致する
- 最低2回の full pass で wall-clock、token cost、人間の判断負荷、failure localization、
  セッション跨ぎ復旧を記録する

さらに **reality anchor**: 内部 gate の通過だけを成功にせず、成果物の下流消費者
（実装者・利用者・fresh-context auditor）による検証を評価へ接続する。

## 評価軸（project-08）

レビューと完成判定で使う5軸:

| 軸 | 問い |
|---|---|
| 構造の可視性 | 暗黙エッジは何件発見・解消されたか。各エッジの出典（どの規約由来か）を特定できるか |
| 失敗の局在化 | 問題を特定のノード・層へ特定できるか |
| 協調コスト | グラフ記述の手間、並列化のオーバーヘッド対効果、承認待ち時間 |
| 観測可能性 | 進行が段階ごとに見えるか。並行サブタスクの状態は明瞭か。判断要求の品質 |
| 信頼性 | グラフ記述と実際の実行が一致するか。合流基準は健全か。timeout は発火するか |
